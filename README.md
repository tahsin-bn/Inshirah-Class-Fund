# Inshirah Class Fund

Transparent class-fund management: monthly contributions, payments, expenses, collector handovers, birthdays and reports, in Bangla and English.

- **Frontend:** React 19, TypeScript, Vite, Tailwind CSS 4, Radix UI primitives, TanStack Query, React Hook Form + Zod, Recharts
- **Backend:** Supabase (Postgres, Auth, Row Level Security, Storage, one Edge Function, pg_cron)
- **Hosting:** Vercel, deployed automatically from GitHub

## How it is organised

```
src/
  pages/public      public, privacy-safe dashboard (no login)
  pages/auth        sign in, first-time owner setup
  pages/app         staff screens (dashboard, months, payments, students, expenses, handovers,
                    collectors, birthdays, reports, users, settings, audit log, profile)
  components/ui     design-system components
  components/domain payment dialog, receipt, student picker, lookups
  lib               Supabase client, data hooks, formatting (Asia/Dhaka, Bangla digits), auth
  i18n              all English/Bangla strings in one dictionary
supabase/
  migrations        the full database: tables, triggers, RLS policies, business functions
  functions         admin-users edge function (creates staff accounts)
  tests             security smoke test (52 checks across all roles)
```

### Security model

| Role | Can do |
| --- | --- |
| Public visitor | Read totals and monthly summaries through `get_public_dashboard()` only. No names, rolls, phones or individual payments. |
| Collector | See and collect from **assigned** students only, hand cash to the treasury, request expenses. |
| Treasurer | Record payments, approve/reject expenses (not their own), confirm handovers, grant waivers, reverse payments. |
| Admin | Everything above plus students, months, users and roles, settings. Cannot change their own role. |
| Auditor | Read-only access to every record, report and the audit log. |

- Roles live in `profiles.role` and can only be changed by an admin through `set_user_role()`; a trigger blocks every other change.
- The browser can only `SELECT` money tables. Every write goes through `SECURITY DEFINER` functions that check the caller's role in the database.
- Payments, expenses and handovers are never deleted. Corrections are reversal or void entries with a reason.
- Every change is written to `audit_logs` by a trigger; nobody can edit it.
- Money is stored as whole taka in `BIGINT` columns. Receipt numbers are generated by database sequences.
- Only the publishable key ships to the browser. The service-role key exists only inside the edge function on Supabase.

### Money rules

- Closing balance = opening balance + collected + other income − approved expenses.
- Each month's opening balance is the previous month's closing balance (`get_month_ledger()`).
- Pending or rejected expenses and cash handovers never change the balance.
- A student owes dues for a month if they joined before it ended and weren't archived before it began.
- Overpayment, duplicate submissions (double-clicks), payments to closed months and self-approval of expenses are blocked in the database.

## Local development

```bash
npm install
cp .env.example .env.local   # fill in your Supabase URL and publishable key
npm run dev
```

## Setting up a new Supabase project

1. Create a project and run the files in `supabase/migrations/` in order (SQL editor or `supabase db push`).
2. Set the owner's email (not committed to Git):
   ```sql
   update app_private.config set bootstrap_admin_email = 'owner@example.com';
   ```
3. Deploy the edge function: `supabase functions deploy admin-users --no-verify-jwt`.
   (It checks the caller itself; the bootstrap call happens before anyone can sign in.)
4. **Authentication → Providers → Email:** turn off **Allow new users to sign up**. Staff accounts are created by an admin from the Users page.
5. Open the app, go to `/setup`, and create the owner account with that email. After this, setup closes for good.

## Deploying on Vercel

1. In Vercel, **Add New → Project** and import this GitHub repository.
2. Framework preset: **Vite** (build `npm run build`, output `dist`; `vercel.json` already sets this and the SPA rewrites).
3. Add these environment variables for Production, Preview and Development:

   | Name | Value |
   | --- | --- |
   | `VITE_SUPABASE_URL` | `https://<project-ref>.supabase.co` |
   | `VITE_SUPABASE_PUBLISHABLE_KEY` | the `sb_publishable_…` key from Supabase → Project Settings → API Keys |

4. Deploy. Every push to `main` deploys production; every other branch gets a preview URL.
5. In Supabase → **Authentication → URL Configuration**, set the Site URL to your Vercel domain.

Never add the `service_role` key to Vercel or to any `VITE_` variable.

## Supabase free plan: what to expect

- **Pausing:** free projects pause after a week of low activity. The nightly birthday job may keep it awake, but don't rely on it; restore from the dashboard if it pauses, or upgrade to Pro ($25/month) once real money is tracked.
- **Database:** 500 MB per project. This app uses a few MB per year for a class of 100.
- **Storage:** 1 GB. Receipt photos are compressed to WebP (≈100–300 KB) and stored once per unique file.
- **Backups:** the free plan has no automatic backups. Export from Reports (CSV) monthly, or run `pg_dump` with the connection string.
- **Email:** the built-in email service only reaches your Supabase team members, which is why staff accounts are created with a temporary password instead of email invitations.

## Testing

`supabase/tests/security_smoke_test.sql` signs in as each role and tries allowed and forbidden actions (52 checks). Run it on a non-production database as `postgres`, then run `security_smoke_test_cleanup.sql`.
